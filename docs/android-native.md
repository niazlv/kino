# Нативное приложение (Kotlin, телефон + Android TV)

С 2026-11 в репозитории живёт **настоящее нативное приложение** в `android/` —
Kotlin + Jetpack Compose + Media3. Оно заменяет Capacitor-оболочку
`web/apps/android/` (та пока остаётся в проде до достижения паритета).

Ключевое отличие от оболочки: стриминг играет **ExoPlayer'ом**, а не hls.js
в WebView. Отсюда то, чего не могло быть: фонное аудио и шторка уведомлений
через MediaSessionService, честный PiP, кодеки по MediaCodecList, D-pad
напрямую через фокусную систему Compose.

## Сборка

```bash
cd android
./gradlew :app:assembleDebug          # отладочный APK
./gradlew -PkinoUrl=http://10.0.2.2:8080 :app:assembleDebug   # против локального core
./gradlew :app:assembleRelease        # релиз: тот же ключ web/apps/android/keystore
```

Готовый APK: `~/Library/Caches/kino-android-native/app/outputs/apk/<variant>/`.
Сборка вынесена из `~/Documents` в Caches — iCloud плодит дубликаты
«X 2.ext» в intermediates (тот же приём, что в старой оболочке).

- applicationId `ru.sorewa.kino`, versionCode с 10 — релизный APK ставится
  **поверх установленного** старого приложения (ключ один и тот же).
- Точки входа: `MainActivity` (телефон) и `TvActivity` (LEANBACK_LAUNCHER,
  баннер из `res/drawable-xhdpi/banner.png`).
- Эмуляторы для smoke: AVD `kino_phone` (android-36 google_apis arm64) и
  `kino_tv` (android-36 android-tv arm64), созданы через `avdmanager`.
  У эмулятора свой DNS не резолвит наш домен — запускать с
  `-dns-server <DNS хоста>`.

Бэкенд не менялся: device-flow уже был готов для нативных клиентов, стриминг —
HLS через шлюз (тикет в пути URL, заголовки не нужны — это делалось ради
нативного HLS). Бинарники качалки (`libkinopub.so` + `libffmpeg.so`, arm64) в
`app/src/main/jniLibs/arm64-v8a/` — не коммитятся, пересборка:
`web/apps/android/tools/build-bins.sh` из соседнего репо `../kinopub-downloader`;
в APK лежат как «библиотеки» с `useLegacyPackaging` (единственный способ
исполнять файлы на Android).

## Проверено в этапе 1 (2026-11-13)

- Релизный APK подписан тем же ключом, что старая оболочка (SHA-256
  6d1114…88a3) — обновление в одно касание; реальный телефон (Xiaomi,
  Android 17) ставится и работает без крашей.
- Вход: неверный пароль → понятная ошибка; ТВ-вход: код с сервера + QR +
  ожидание одобрения. Smoke поймал баг сериализации Any (post/put получили
  reified-тип тела).

## Этап 2: качалка, офлайн, пульты (2026-11-13)

- **Качалка нативная**: тот же движок kinopub-downloader (MKV с дорожками не
  умеет ни Kotlin, ни MediaMuxer), обвязка переписана: persistent-очередь,
  foreground-сервис, NDJSON-прогресс в уведомлении, пауза/отмена/reap,
  экспорт в `Movies/kino/<Тайтл>/SxxEyy.mkv` или SAF-папку на выбор.
- **Офлайн-просмотр**: без сети приложение превращается в витрину скачанного
  (баннер + «Повторить»); на входе — кнопка «Смотреть скачанное» (видна сразу,
  без попытки войти). Локальный плеер PlayerActivity (mode=local): позиция и
  просмотренность — в локальной библиотеке, ≥92% = просмотрено, по концу —
  следующая непросмотренная серия тайтла (марафон). Кадры и постеры — локально
  (Art), длительность из файла.
- **Adopt**: подбрасанные/старые файлы в `Movies/kino/` и SAF-папке подбираются
  в библиотеку (дедуп по uri и отпечатку title+s/e+size), кадры вытягиваются
  при подборе.
- **Синк**: dirty-прогресс докладывается серверу при старте приложения,
  открытии загрузок и появлении сети; безымянные (adopted) тайтлы связываются
  через подсказки.
- **Настройки**: «только Wi-Fi», папка загрузок (SAF), выход.
- **ТВ**: «Загрузки» в рельсе, офлайн-витрина та же, на офлайн-логине — кнопка
  скачанного; всё ходится с пульта.

Проверено на эмуляторах (2026-11-13): офлайн-витрина с баннером, adopt
подброшенного MKV → запись в библиотеке, кадр извлекается и рисуется, локальный
плеер доигрывает до конца → «просмотрено» → раздел «Просмотрено» с «Сначала»;
ТВ: офлайн-логин → «Смотреть скачанное» → витрина, разрешение на медиа и
навигация с пульта. 17 юнит-тестов (argv, NDJSON, имена/отпечатки/папки).
Отмеченный краш ExoPlayer'а без WAKE_LOCK пойман и починен разрешением.

**Не проверено без аккаунта** (нужна сессия на эмуляторе — вход там работает,
либо код приглашения): полная качалка серии с прода до конца, доклад прогресса
на сервер, связывание adopted-тайтлов.

## Переделка интерфейса (2026-11-13)

Первая версия выглядела сырой и местами не работала. Что было сломано и
исправлено:

- **Видео не играло вообще**: шлюз отдаёт адрес потока относительным
  (`/stream/tkt_…/master.m3u8`), ExoPlayer принимал его за файл на
  устройстве. `Api.absolute()` достраивает адрес потока и субтитров.
- **Постеры и кадры не грузились**: Coil ходил без cookie, а `/titles/:id/art`
  отдаёт картинки только с сессией. `KinoApp` — `ImageLoaderFactory` на
  OkHttp-клиенте API (cookie + обновление по 401), с дисковым кешем.
- **Чёрный текст на тёмном фоне** вне Scaffold — корневой `Surface` в теме.
- **Иконка приложения невидима**: фон адаптивной иконки был тёмным под
  тёмным билетом — снова зелёный #3ddc84, как у оболочки; заставка
  Android 12+ — знак на зелёной плашке (`values-v31/themes.xml`).
- **Вход на ТВ был тупиком**: телевизор просил «ввести код на телефоне», а
  в приложении такого экрана не было. Теперь «Профиль → Подключить
  устройство»; код показывается целиком («ABCD-EFGH», раньше резался
  `chunked(3)`), ТВ представляется серверу как `tv`.
- **Обновление поверх старого приложения выкидывало на вход**: сессия
  витрины жила в cookie WebView (`app_webview/Default/Cookies`), нативное
  приложение её не видело. Теперь переносится — см. «Переезд со старой
  оболочки» ниже.
- Мелькание экрана входа при каждом холодном старте (сессия читалась с
  диска после первого кадра) — до чтения показывается пустой фон.

Как выглядит: главная — крупная карточка «Продолжить» с кадром серии и
кнопкой «Смотреть 2×5», ленты (начатое, новые серии, буду смотреть, новинки);
тайтл — размытый постер фоном, кнопка следующей серии («Продолжить 1×1»,
«Смотреть 2×6», «Пересмотреть»), отметки иконками, сезоны таблетками, серии
с кадрами и меню «просмотрено/скачать»; на ТВ — афиша, меняющаяся вслед за
фокусом, и прокрутка «по необходимости» (`MinimalScroll`: Compose на ТВ по
умолчанию тянет фокус к трети экрана и уводит шапку).

Проверено на эмуляторах kino_phone и kino_tv против боя (тестовый
пользователь): вход паролем, сессия переживает перезапуск, ТВ вошёл по коду,
подтверждённому с телефона; серия играет и на телефоне, и на ТВ с пульта.

## Переезд со старой оболочки (0.1.x → 0.2.0)

Нативное приложение ставится **обновлением** поверх Capacitor-оболочки:
тот же пакет `ru.sorewa.kino`, тот же ключ (SHA-256 `6d1114…18a3`, схема
v2, как у опубликованной 0.1.8), versionCode 10 > 9. Старая оболочка сама
найдёт его в `/app/version.json` и предложит обновиться; данные пакета
остаются. Что откуда берётся (`data/LegacyShell.kt`):

| Что | Где у оболочки | Как переезжает |
|---|---|---|
| Вход | cookie `kino_session` в WebView (HttpOnly, 30 дней) | `AuthRepository.adoptWebViewSession`: `/me` с этой cookie → device-flow, одобренный ею же → пара токен/refresh (180 дней); cookie-сессия гасится на сервере, cookie стирается из WebView |
| Скачанное | `files/library.json` (org.json), файлы в MediaStore/SAF | тот же файл и формат — читается как есть (тест `reads library json written by the old shell`) |
| Кадры, постеры | `files/art/e<hash>.jpg`, `t<id>.jpg` | те же имена |
| Папка загрузок | prefs `downloads` → `tree` | тот же ключ, SAF-разрешение у пакета остаётся |
| «Качество», HEVC/AV1, сводка | prefs `downloads` → `settings/maxq|hevc|av1|stats` | `LegacyShell.importSettings`, один раз, только незаданное здесь |
| Пропуск заставок, «следующая серия», оценка канала | localStorage витрины `kp.skip`, `kp.autonext`, `kino.bw.*` | то же; читается пустой страницей с происхождением витрины без сети |
| ТВ | `MainActivity` на обоих лаунчерах, ТВ = leanback или «Режим телевизора» (`kino.tv`) | `MainActivity` на таком устройстве уводит в `TvActivity` (ярлыки и «избранное» лаунчера ведут на старую активность) |

Исходы переноса входа: cookie нет или сервер ответил 401 — обычный вход;
сервер не ответил — офлайн-витрина скачанного, cookie остаётся, «Повторить»
пробует снова. Истёкшую cookie WebView не отдаёт — у такого человека и
старое приложение уже просило войти.

Новое для обновившихся: при первом заходе в «Загрузки» система спрашивает
доступ к видео (подбор чужих файлов из `Movies/kino`); отказ ничего не
ломает — своё скачанное видно и так.

**Найдено и исправлено при проверке (2026-11-13):**

- `TokenStore.saveSession(displayName = …)` после `/me` записывал пустой
  токен по умолчанию — перенос сессии сразу разлогинивал. Теперь пишется
  только переданное.
- Обмен на пару после входа паролем обрывался: сохранённый токен уводил
  интерфейс со входа, корутина экрана отменялась после `/auth/device`, и
  вход жил 30 дней без продления. Дообмен — в `NonCancellable`; парольная
  сессия гасится, как только есть пара.
- Ответ 401 на `/auth/refresh` (погашенная сессия, «Выйти на всех»,
  истёкший refresh) клал приложение навсегда: refresh шёл клиентом с
  `Authenticator`, тот ждал `refreshMutex`, который держал этот же refresh.
  Все запросы висели, на экране — скелетоны при каждом запуске. Теперь
  refresh, вход и гашение чужой сессии идут клиентом без него (`Api.bare`).
- Нечитаемый `library.json` больше не затирается первой записью — копия
  остаётся рядом (`library.json.unreadable`).

**Как проверено:** временный эмулятор (API 36) + лёгкий стенд (core из
HEAD, свои Postgres/Redis, витрина vite) — старая оболочка 0.1.8 из
исходников, нацеленная на стенд: вход, настройки, опись → `adb install -r`
нативной сборки → главная без входа, настройки и «Загрузки» на месте,
на сервере одна живая сессия с refresh. Отдельно: обновление при лежащем
сервере (офлайн → «Повторить» → вход перенесён), выход держится после
перезапуска, вход паролем даёт пару, погашенная сессия ведёт на вход,
`kino.tv` → `TvActivity`. Релизный APK сверен с опубликованным 0.1.8
(`publish-apk.sh --check`). На живом телефоне с боевой cookie не
проверялось.

## Подсмотрено у Kino.Watch (2026-11-13)

Разобран официальный Kino.Watch 2.25 (экраны + строки APK). Перенесено то,
что делается на стороне приложения:

- Плеер: надписи ВИДЕО/АУДИО/СУБТИТРЫ стали «таблетками» с текущим выбором
  («1080p (авто)», озвучка, «Выкл»); справа вверху часы и время окончания
  серии с учётом скорости; кнопка «i» — сводка о потоке (кодек, кадр,
  битрейт, площадка, канал, буфер); свайпы у краёв: слева яркость окна,
  справа громкость. Настройки: «Прятать панель через 3/5/10 с/никогда»,
  «Свайпы», «Сводка о потоке всегда».
- Тайтл: постер слева, сводка справа (вид · год · статус, сезоны · серии,
  плашки «N озвучек / N источников», жанры); блок «Озвучки» по следующей
  серии (`/episodes/:id/voices`); список серий «Компактно».
- Скачивание: «Выбрать серии» — галочки по сезонам, по заданию на серию.

Не перенесено — нет данных в API: оценки IMDb/КП, страны, даты выхода
серий и «следующая через N дней», значки качества/AC3 у тайтла, актёры,
похожие. Выбор озвучки при скачивании — ждёт сверки имён дорожек.

Найдено попутно: nginx/1.26.0 перед боевым доменом на внешнем адресе
(77.66.186.50) отвечает 414 на адреса потока ЛордФильма — шлюз кодирует
их в путь длиной ~8,5 КБ, больше дефолтного `large_client_header_buffers`
8k. Изнутри сети (Caddy напрямую) не воспроизводится.

## Админка с телефона (2026-11-13)

«Профиль → Аккаунт → Админка» — только у роли admin и не на ТВ
(`util/Admin.kt`). Открывает `/admin/` во вкладке браузера поверх
приложения (Custom Tab, сначала Chrome, иначе браузер по умолчанию).
Вёрстка админки уже узкая, переписывать её не нужно.

Почему не WebView и не «ссылка со входом» из приложения: токен приложения —
один фактор и живёт до 180 дней (refresh), а на ТВ под тем же именем он
тоже есть. Выдай он вход в админку — второй фактор перестал бы что-либо
значить. Поэтому вкладка входит сама, своим путём: passkey (отпечаток,
работает в Chrome, в WebView — нет) или пароль + код; сессия в cookie
браузера живёт 12 ч. Ключ для телефона добавляется один раз в своей
карточке админки, открытой с самого телефона.

Приложение открывает `/admin/login?passkey=1`: страница входа сама
запускает ключ — нажатие «Админка» сразу спрашивает отпечаток. Только если
в этом браузере ключ уже срабатывал (метка `kino-admin-passkey` в
localStorage ставится после удачного входа, подтверждения или добавления
ключа) — иначе на устройстве без ключа вместо формы выскочило бы пустое
системное окно. Отказ на автозапуске — мягкая подсказка, кнопка и пароль
на месте; живая сессия со страницы входа уводит сразу в админку
(`internal/transport/httpadmin/static/passkey.js`).

## Главный экран Android TV (2026-11-14)

Как у Kino.Watch («kino.watch: Новые фильмы»), только на телевизоре
(leanback + системный TvProvider, Android 8+; на телефоне всё — пустые
вызовы). Пакет `tvhome/`.

- **«Продолжить просмотр»** (системная строка Play Next / Watch Next) — то
  же, что лента «Продолжить» (`/continue`, до 15): начатое — `CONTINUE` с
  позицией и длительностью (полоска прогресса), следующая серия — `NEXT`.
  Порядок — время последнего касания тайтла из `/history` (лаунчер
  сортирует карточки всех приложений по нему; «сейчас» при каждом
  обновлении выталкивало бы наши наверх). Карточку, убранную человеком,
  не возвращаем, пока не сдвинется просмотр (другая серия или позиция).
- **Канал «Новые серии»** (`/new-episodes?only=new`, до 20) — постеры с
  подписью «N новых серий», карточка открывает тайтл. На главный экран —
  только с согласия: системный диалог «Add the channel … to your home
  screen?» один раз сам после входа (если есть что показать), дальше —
  «Профиль → Главный экран → Канал «Новые серии»» (там же виден статус).
- **Нажатие на карточку** — `intent:`-ссылка с пакетом в
  `TvLinkActivity` (батут без окна): `play` — сразу `PlayerActivity` с
  серией (продолжит с места), `title` — тайтл в ТВ-оболочке. Плеер жив в
  фоне и нажата другая серия — экран пересоздаётся с новой (только ТВ).
  Сессию погасили на сервере — плеер уводит на вход, а не стоит на кадре
  прошлого потока.
- **Картинки**: лаунчер — чужой процесс без нашей cookie, а `/art`
  отдаётся только с сессией. Приложение качает кадры (16:9) и постеры в
  `files/tvhome` и отдаёт через `TvArtProvider` (`<пакет>.tvart`, только
  чтение). Провайдер открыт всем, поэтому имена — хеш ключа с солью
  установки; нет картинки на сервере (404) — повтор через сутки.
- **Когда обновляется**: при каждом возвращении в приложение и сразу после
  входа (`TvActivity`), через 1,5 с после ухода из приложения и через 5 с
  после закрытия плеера (WorkManager, дождаться отчёта о позиции), и раз в
  2 часа в фоне (новые серии выходят, пока телевизор стоит).
- **Выход** (`AuthRepository.logout` → `onSignedOut`) стирает строки, канал,
  картинки и соль, снимает фоновые задачи; новый вход снова спросит про
  канал. Фоновое обновление, получив 401, переспрашивает `/me` и при
  подтверждённой 401 тоже всё стирает.

Ловушка: `PreviewChannelHelper.getAllChannels()` читает каналы без колонки
`browsable` — `PreviewChannel.isBrowsable()` там всегда false; видимость
канала — своим запросом к `Channels.CONTENT_URI`.

Проверено на временном ТВ-эмуляторе (android-36 android-tv, лаунчер

## Плеер не стоит на чужом кадре (2026-11-14)

Было: `maybeStart` ждал `/titles/:id` (список серий и запомненный выбор),
а `loadDetail` молча глотал его ошибку — плеер не выпускал тикет вовсе и
показывал то, что осталось в общей службе: кадр прошлого потока с
0:00/0:00, без ошибки и без «Повторить». Попадали и телефон, и ТВ (сеть
моргнула, 5xx у core).

Стало (`PlayerActivity`):

- **Тайтл не приехал — всё равно старт.** Быстрый сбой — повтор через
  1,5 с; второй сбой, таймаут (дольше 5 с) или 401/404 — старт без
  тайтла: без «следующей»/«предыдущей», без запомненных площадки и
  озвучки (сервер их сам не подставляет), шапка пустая. Сорвётся и выпуск
  тикета — ошибка клиента («нет связи с сервером», «сессия кончилась…»)
  с «Повторить». Список серий добирается в фоне (через 10 и 30 с) —
  «следующая» появляется, шапка заполняется. 401 на ТВ до старта —
  по-прежнему уход на вход.
- **Пока ждём тайтл — кольцо** (`PlayerViewState.opening`), а не пустой
  экран.
- **Чужого кадра нет.** Служба (её ExoPlayer) живёт дольше экрана, и
  `onDestroy` только ставит поток на паузу. Новый экран при подключении
  к службе убирает прежний поток (`stop()` + `clearMediaItems()`; именно
  в таком порядке — пустой список в READY дал бы `STATE_ENDED`, а тот —
  «серия кончилась» и автоследующую). Фоновую игру это не задевает: она
  живёт, пока жив тот же экран (`singleTask`; у сессии нет
  `sessionActivity`, шторка экран заново не создаёт, возврат — через
  задачу приложения). Смена серии на виду (кнопки, список, автоследующая
  в PiP) тоже сначала убирает прежнюю: не виден её кадр, не идёт её звук.
  В фоне (автоследующая под шторкой) — нет: пустой список снял бы
  уведомление и foreground (Media3 1.8 держит foreground 10 мин после
  паузы/конца, но не при пустом плеере), а вернуть его из фона
  Android 12+ не даёт.
- Попутно: в режиме скачанного старт ждёт и службу, и запись библиотеки
  (раньше служба, подключившаяся первой, роняла `localEntry!!` в «не
  удалось запустить плеер»).

Рубильник для проверки (только debug-сборка):
`adb shell setprop debug.kino.failtitle 503` — `/titles/:id` «отвечает»
503 (`0` — нет связи, `401` — сессия), `503x1` — ломается только первая
попытка; снять — `setprop debug.kino.failtitle ""`. Соседний
`debug.kino.failsource <площадка|all>` портит адрес потока.

Проверено на временных эмуляторах (телефон android-36 google_apis и ТВ
android-36 android-tv) против боя, тестовый пользователь, вход кодом:

- телефон: S1E1 играл → «Назад» → S1E2 с `failtitle 503` — 0,7 и 2 с
  чёрный экран с кольцом (кадра S1E1 нет), после повтора старт без
  тайтла, серия играет; рубильник снят — фоновый повтор заполнил шапку
  («РИК И МОРТИ S1E2 · Пёс-газонокосильщик»), появились пред./след.;
  `503x1` — повтор удался, старт обычный (с места, с названием в шторке);
  «Следующая серия» в плеере — шапка S1E3 на чёрном с кольцом, без кадра
  S1E2; сеть выключена — «нет связи с сервером» + «Повторить» на чёрном,
  сеть включена → «Повторить» играет; конец S1E2 в PiP → S1E3 сам в PiP,
  служба осталась foreground, шторка с новым названием;
- ТВ (через ссылку карточки главного экрана, как Watch Next): то же с

  отрезана (`cmd connectivity set-package-networking-enabled false`) —
  первый `/titles` висит до таймаута OkHttp (40 с) с кольцом, затем
  ошибка, фокус на «Повторить», OK после возврата сети — играет; `401`
  до старта — уход в `TvActivity`, ничего не играло.

Мелочь, не исправлена: в первые доли секунды после очистки «таблетка»
качества ещё показывает высоту прошлого потока («402P (АВТО)») —
`videoSize` контроллера обновляется чуть позже.

## Офлайн «как онлайн» (2026-11-21, 0.2.10)

Просьба перед перелётом: без сети скачанные сериалы и фильмы должны выглядеть
как онлайн — обложка, название, описание, сезоны, серии с названиями и
кадрами. Раньше офлайн-витрина была плоским списком файлов.

- **Карточки тайтлов на устройстве** — `data/OfflineCatalog.kt`: ответ
  `/titles/<id>` (+ студии озвучки) в `files/offline/t<id>.json`. Пишется после
  каждой докачки (DownloadService → `refreshTitle(force)`), при открытии
  страницы тайтла с сетью, если у него есть скачанное, и при каждом запуске с
  сетью (`AppContainer.warmUpOffline()` → `warmUp`: прогресс серверу, связь
  безымянных файлов с каталогом, кадры из файлов, карточки). Свежая карточка
  (< 6 ч) и уже обойдённые картинки повторно не тянутся. Карточки не успели
  сохраниться — `detailFor` собирает страницу из самих файлов.
- **Картинки** — `data/Art.kt`: постер `t<id>.jpg` (480 px), кадры серий
  с сервера `s<episodeId>.jpg` (скачанные серии первыми, затем остальные серии
  их сезонов, потолок 300), кадр из файла `e<hash>.jpg`. `PosterImage` и
  `ShotImage` берут файл с диска раньше сети — без сети картинки те же.
  `.none` только на 404/мусор: сетевой сбой не запрещает повтор навсегда
  (раньше постер, не скачавшийся однажды, не появлялся никогда).
- **«Загрузки»** — тайтлы постерами (сколько серий, вес, непросмотренные),
  «Продолжить» по начатым сериям, внизу место и строка «Готово к просмотру без
  сети» / «Готовлю… N из M» / «Сохранить». Долгое нажатие на постер — стереть
  тайтл целиком.
- **Страница тайтла** — та же `TitleScreen`: без сети (или сервер молчит > 4 с)
  — сохранённая карточка, отметки и «Скачать» скрыты, под кнопкой «Без сети ·
  на телефоне N из M серий», нескачанные серии приглушены. Скачанная серия
  **всегда играет с телефона** (и с сетью — как просили для старой оболочки
  06.09), в меню серии «Смотреть онлайн» и «Стереть с телефона». Таблетки
  сезонов: ✓✓ — досмотрен, значок загрузки — есть скачанное. Офлайн-позиции
  (`withLocal`) поверх карточки; с сетью — только неотправленные (dirty).
- **Офлайн-корень** — свой NavHost: «Загрузки» с плашкой → `title/{id}`
  (`offlineOnly`) и `local?name=` для файлов без тайтла. Нет сети вовсе
  (`hasNetwork()`, режим полёта) — офлайн сразу, без ожидания `/me`. Сеть
  пропала совсем — `dispatcher.cancelAll()`: зависшее HTTP/2 не держит экраны
  до 40 с.
- **Плеер файла** — названия серий из сохранённой карточки.

Найдено и исправлено попутно: DownloadService держал свой экземпляр
`LocalLibrary` — первая же запись позиции из плеера затирала серии, скачанные
службой; подбор файлов (`adopt`) из офлайн-корня и «Загрузок» шёл одновременно
и добавлял файл дважды (замок + схлопывание дублей при чтении); экраны не видели
позицию из плеера (он пишет её в `onStop`, после `onResume` экрана) — теперь
`LocalLibrary.changes`.

Проверено на временном эмуляторе (API 34) против боя с тестовым пользователем:
скачаны 3 серии «Масяни» через приложение → карточка, постер и ~150 кадров на
устройстве; режим полёта → холодный старт сразу в офлайн-«Загрузки» с постером;
страница тайтла как онлайн; серия играет, название серии в плеере; позиция
видна на странице и в «Продолжить»; сеть вернулась → «Повторить» → позиция на
сервере; сеть пропала посреди работы → страница тайтла из карточки за ~2 с;
файл без тайтла → страница по названию папки. Тесты `OfflineMergeTest`.
Часть кадров сервер отдаёт 502 — для скачанных серий тогда кадр из файла.

## Загрузки: готовое не пропадает, автоповтор (2026-11-22, 0.2.11)

Жалоба со скрина: «Последняя загрузка не удалась» и строка INFO из лога.
Сезон «Даже у студсовета есть косяки!» (title 56975): у kinopub 7 серий,
8-ю отдаёт аниме-площадка, а её `master.m3u8` — это сразу плейлист сегментов,
без `#EXT-X-STREAM-INF`. Утилита падала «no variants found in master
playlist», задание завершалось с кодом 1, и служба не переносила **ни одной**
из 7 готовых серий (экспорт был только при полном успехе). На экран шла
случайная строка: stderr копился до 8000 символов с головы.

- **Утилита** (kinopub-downloader b6ef21e): media-плейлист на адресе мастера —
  один вариант (`parseMasterPlaylist`), выбор качества берёт ближайшее.
  `libkinopub.so` = v0.9.2-3-gb6ef21e (прежняя сборка 13.11 — те же коммиты,
  тогда ещё незакоммиченная правка резолвера 3869e93).
- **Готовое — при любом исходе.** `Exporter.readyFiles` читает состояние
  утилиты (`<work>/<серия>/.kinopub-state.json`: путь, название, ссылка на
  тайтл) и переносит только сшитые серии; недосшитый файл без записи в
  состоянии не трогается. Остатки прошлых прогонов забираются при старте
  приложения (`DownloadService.kickIfNeeded` из AppRoot и «Загрузок»).
  Состояние стирается, только когда задание скачано целиком, — поэтому повтор
  докачивает лишь недостающее.
- **Причина** — по серии и по-русски (`Downloader.describeFailure`), stderr —
  хвост 12 000 символов.
- **Автоповтор**: 3 запуска, паузы 30 с и 2 мин; без сети ждёт её до 30 мин
  (dataSync-службе Android даёт 6 ч в сутки), дальше очередь ждёт следующего
  открытия приложения. Карточка с обратным отсчётом и «Повторить сейчас».
- **«Повторить»** на экране и в уведомлении; сдавшееся задание помнится в
  prefs и после перезапуска. `--force` — только ручным заданиям, у которых
  утилита всё пропустила (файл давно перенесён и, может, стёрт).
- Попутно: `onCreate` службы добавлял сохранённую очередь в саму себя (каждое
  задание качалось дважды); отмена стирала готовые серии.

Проверено на временном эмуляторе против боя (тестовый пользователь): остатки как у
пользователя (2 серии в состоянии + 1 недосшитая) → после запуска 2 перенесены
в «Фильмы/kino» и в опись с titleId, недосшитая на месте; 8-я серия качается
новой `libkinopub.so` (720p, 194 МБ), обрыв сети посреди — утилита сама
откладывает серию и докачивает после возврата сети. **Не проверено**: убитый
процесс утилиты → автоповтор службы (эмулятор погас, сервер вне домашней сети
недоступен); на телефоне пользователя — не проверено.

## Загрузки видно: фильм не «Готово» впустую (2026-11-23)

Жалоба со скрина (22.11, 0.2.11): на фильме «Впритык» нажал «Скачать» три-четыре
раза — ни полосы на странице, ни карточки в «Загрузках», в уведомлениях только
«Готово». По `dumpsys usagestats` телефона: служба стартовала в 05:39:39,
05:40:03 и 05:40:23 и каждый раз жила 1–2 с; в «Фильмы/kino» фильма нет.

- **Причина.** У фильма на платформе `seasonNo = 0`, шторка слала утилите
  `#/title/<id>/s0e1`; `ParsePlatformLink` сезон 0 отвергает, утилита за
  секунду печатает `{"type":"result","total":0,…,"error":"input URL is
  invalid or unclassified"}` и выходит с кодом 1. Фильмы в нативном
  приложении не качались с 0.2.0 (до 0.2.11 — с видимой ошибкой). Ссылку
  чинит шторка (соседняя правка в `DownloadDialog.downloadJobs`: фильм —
  `$base`, как у витрины; серия сезона 0 — по id серии).
- **«Готово» на сбое — регрессия 0.2.11.** Служба считала сбоем только
  упавшие серии и код ≠ 0 *без* строки `result`; ошибка всего прогона
  (`result.error`) и ноль скачанного шли «Готово». Теперь решение в чистой
  `Downloader.outcome()` (тесты `OutcomeTest`): ошибка прогона, ноль серий без
  пропусков, `--force` со всем пропущенным — сбой с причиной по-русски;
  неверная ссылка / нет такой серии — `permanent`, сдаётся сразу без трёх
  автоповторов. Удача без переноса (автоповтор, всё уже было) — «Уже скачано».
- **Страница тайтла знает о качалке** (`TitleDownload.kt`, тесты
  `TitleDownloadTest`): кнопка «Скачать» — кольцо «Качается 37%» / «В очереди» /
  «На паузе» / «Не скачалось»; под кнопками полоса «Фильм качается · 37% ·
  512 МБ из 1,4 ГБ» (касание — во вкладку «Загрузки», у сдавшегося —
  «Повторить»); у серий — кольцо с процентами или часы «в очереди загрузок».
  Фильм, который уже качается, по «Скачать» открывает «Загрузки». Серия
  утилиты «S01E01» сопоставляется с карточкой и при сезоне 0 (`utilityKey`).
- **«Загрузки»:** карточка «В очереди · сейчас начнётся / жду сеть», пока
  задание стоит, а качалка ещё не пошла (переносит прошлое или ждёт сеть);
  свежее задание без сети больше не рисуется красным «Загрузка не удалась»
  (`retryAt` только у настоящего автоповтора). В строке — «серия 2 из 8»
  (`epTotal/epDone` в статусе), до первых байтов — «готовлю загрузку…» и
  бегущая полоса.
- **Задание переживает смерть процесса.** 22.11 HyperOS убил процесс через
  4 мин после ухода из приложения посреди 14-й серии «Басни»: 13 готовых
  лежат в рабочей папке (перенесутся при открытии приложения), а само
  задание пропало — из очереди его вынули при старте. Теперь идущее задание
  пишется в prefs (`running_job`, `commit()`), `onCreate` службы возвращает
  его в голову очереди, `kickIfNeeded` считает его делом.

Проверено: юнит-тесты (62, все зелёные), утилита с ссылками `s0e1`/`s0e0`/
`s1e1` против боя (строка `result` выше), журнал службы на телефоне
пользователя (только чтение). **Не проверено** вживую на устройстве: эмуляторов
нет, а входа без SQL на бою (ssh только из домашней сети) не завести.

## Офлайн-стейт: ничего не теряется молча (2026-11-23)

Ступень 1 плана serverless-режима: пользовательский стейт — источник истины
на устройстве, сервер — синк при появлении сети. Сервер (Go) не менялся:
у `PUT /progress` уже были `deviceId`+`client_ts` и правила слияния (тот же
девайс — «кто последний», разные в окне 5 минут — «кто дальше досмотрел»),
метки — полный replace, prefs — частичный патч. Приложение просто начало
ими пользоваться.

- **`StateStore.kt` (`files/state.json`)** — очередь мутаций + кэш чтений,
  в идиоме `LocalLibrary` (атомарный tmp+rename, `changes: StateFlow`).
  Мутация (позиция, галочка, метки, озвучка) встаёт в очередь **до** похода
  в сеть; ack вычищает запись по совпадению ts — свежее, вставшее в очередь
  пока запрос летел, не трогается. Рядом кэш: метки тайтлов (до 200) и
  последняя страница «Продолжить». Семантика очереди — чистые функции
  (`mergeProgress`/`mergeWatched`/`mergePrefs`/`overlayEpisodes`/
  `resolveMarks`/`overlayContinue`, тесты `StateStoreTest`): «смотрел»
  ставит позицию в конец, «не смотрел» её обнуляет (сервер удаляет строку —
  воскрешать позицию после галочки нельзя), патчи озвучки сливаются по
  полям.
- **Прогресс стрима больше не теряется.** `PlaybackClient` каждый репорт
  (тик 15 с, финальный, конец серии) кладёт в очередь, потом шлёт `PUT
  /progress` с `deviceId` из TokenStore — раньше ошибка сети съедала позицию
  молча, а deviceId вообще не уходил (сервер подставлял id сессии, и
  слияние «один девайс на сессию» работало случайно). Восстановление
  позиции при старте сперва смотрит в очередь — своё несохранённое сильнее
  сервера.
- **Метки переживают офлайн и сбой.** `setMarks` (телефон, ТВ, «убрать из
  „Продолжить"») — очередь+кэш до PUT, ack после ответа; страница тайтла
  без сети рисует строку отметок из кэша и очереди (раньше `ActionsRow`
  в офлайне не рисовалась вовсе). В очередь идут **только изменённые поля**
  (`MarksPatch` из `marksDiff`), не снимок: при отправке `syncPendingState`
  сперва читает серверные метки и кладёт своё поле поверх — PUT меток
  заменяет целиком, и снимок из кэша затёр бы метки, поставленные с другого
  устройства, пока мы были офлайн. Кэш для показа остаётся снимком; патч без
  базы на странице не показывается (переключатели скрыты), но к отправке
  годен. Отметка сезона идёт по сериям в очередь — сорвавшийся PUT не
  теряет ни одной галочки.
- **Озвучка/площадка переживает сбой.** `persistPrefs` плеера — очередь
  до PUT; ждущий патч ложится и на `prefs` тайтла (`applyPrefsPatch`),
  так что выбор, не доехавший до сервера, виден на странице и в старте
  плеера.
- **Галочка «просмотрено» в офлайне** для нескачанной серии из сохранённой
  карточки идёт в очередь (id у карточек настоящий; у собранных из файлов
  — отрицательный, их сервер не знает и такие не ставятся).
- **«Продолжить» без сети.** Дом сохраняет удачную страницу 0; в офлайне
  показывает её с ждущими позициями поверх, досмотренное в самолёте
  выпадает — как и на сервере.
- **Синк очереди.** `Sync.syncPendingState()`: метки → prefs, потом по
  сериям позиция → галочка; ts записи уезжает как `client_ts`, частично
  доложенное остаётся в очереди (повтор с тем же ts идемпотентен). Внутри
  — `tryLock`, два триггера не шлют одно дважды; пустая очередь и нет
  сессии — мгновенный выход. Триггеры: запуск (`warmUpOffline`), возврат
  на страницу тайтла, **сеть вернулась** (`onAvailable` в `AppContainer`).

Проверено: юнит-тесты (95, все зелёные), `assembleDebug`. Сервер не менялся.
**Не проверено** вживую на устройстве: сценарий «авиарежим в середине серии
→ отметки офлайн → сеть → всё уехало» — за следующим прогоном с телефоном.

## Режим «на этом устройстве»: локальный движок (2026-11-23)

Приложение может работать без сервера: внутри APK лежит `libkinoengine.so` —
тот же Go-код платформы (`cmd/engine`, ADR-0015), собранный под Android. Режим
выбирается на экране входа («Работать на этом устройстве, без сервера») и в
Профиле («Подключение»); сервер остаётся режимом по умолчанию, и у тех, кто
ничего не трогал, ничего не меняется.

**Как устроено**
- `engine/LocalEngine` запускает бинарь из `nativeLibraryDir` подпроцессом
  (`ProcessBuilder`, как и `libkinopub.so`), ждёт `/api/v1/health`, а если
  процесс умер — поднимает заново **на том же порту** (после `maxRestarts`
  подряд сдаётся: `FAILED`, «Повторить»). Адрес приложения (`127.0.0.1:порт`)
  известен ещё до первого запуска, поэтому `Api` строится сразу и о
  перезапусках не знает.
- Порт выбирает приложение, токен — тоже: 32 случайных байта в
  SharedPreferences `connection` (`engine_token`), движок получает его как
  `ENGINE_TOKEN`. Приложение ходит с ним в cookie `kino_session`, как с обычной
  сессией; другого входа в локальном режиме нет. Сервер-сессия при этом
  **сохраняется** — вернуться можно в любой момент.
- Жизнь движка привязана к stdin (`ENGINE_EXIT_ON_STDIN_EOF=1`): приложение
  держит пайп открытым, умерло — пайп закрылся — движок вышел сам и освободил
  порт. Проверено на телефоне: `force-stop` — сирот нет.
- `EngineGate` (OkHttp-перехватчик) держит запрос, пока движок не готов:
  первые секунды после старта порт ещё закрыт. Не поднялся — `IOException`,
  то есть привычное «нет связи».
- **Изоляция данных.** Идентификаторы серий движка и сервера не совпадают, а
  очередь неотправленных отметок (`StateStore`), опись скачанного, кэши
  карточек и постеров на них ссылаются. Поэтому у локального режима свой
  профиль: `files/local/*` (через `ModeContext`) и свой DataStore
  (`kino_local`). Очередь, набранная для боевого сервера, не уйдёт в движок и
  наоборот. Режим серверный получает прежний контекст — данные существующих
  установок остаются там, где лежали.
- **Смена режима — перезапуск процесса** (`AppRestart`, приём ProcessPhoenix:
  активность в процессе `:restart` запускает приложение заново и убивает
  себя). `Application.onCreate` в процессе `:restart` контейнер не строит —
  иначе там поднимался второй движок на той же базе (поймано на телефоне).
- Cleartext: `network_security_config.xml` разрешает открытый HTTP **только**
  `127.0.0.1` и `localhost` (debug — любой, как раньше).

**Чего в этом режиме нет (осознанно, первая версия)**
- По умолчанию включена одна площадка — Анилибрия; остальные включаются в
  «Профиль → Локальный движок → Источники». Бесключевые аниме-площадки на
  проверке (поиск → тикет → настоящий сегмент) играют: Анилибрия, AnimeGo .me и
  .fr, Jut.su .net/.tv/.org, YummyAnime; AniDub нашёл тайтл, но серий не отдал.
  Источникам с ключом (Filmix, Alloha) ключ вводится вручную. kinopub можно и
  по-другому — войти по коду (ниже); введённый руками access-токен приложение
  продлевать не умеет, а сессию, полученную входом по коду, движок продлевает сам.
- «Подключить устройство», смены пароля, выхода, обновлений через сервер и
  админки — они про сервер. Скрыты в интерфейсе; сервер на запрещённые вызовы
  отвечает 403.
- Телевизора: переключатель — только на телефоне.
- iOS: движок там возможен только внутри процесса (gomobile), в этой работе не
  затронут.

**Подпись (User-Agent) движка (23.11).** Движок не выдаёт себя за чужой браузер: подпись
браузероподобная, но кончается `KinoPlatform-Android/<версия приложения>` (приложение
передаёт пометку в `ENGINE_APP_UA`; версия — `BuildConfig.VERSION_NAME`). Устройство
подписи — в ADR-0015 («User-Agent: честный по умолчанию…»). В «Профиль → Локальный движок»
(экран целиком предупреждает, что настройки чувствительные) есть раздел **«Для опытных:
User-Agent»**: показано, с какой подписью движок ходит сейчас, красным — «не советуем
менять, на вашей совести», кнопка «Задать свою подпись…» раскрывает поле «Для всех площадок»
и поле каждой включённой площадки (сильнее общего), «Вернуть подписи по умолчанию»
сбрасывает; заданное уходит на площадку как есть, без пересборки, после «Применить»
(перезапуск движка). Проверка поля — только валидность заголовка: печатный ASCII, до 512
символов (иначе «Применить» недоступно). Переменные окружения: `ENGINE_USER_AGENT`,
`ENGINE_UA_<ID>` (id заглавными).

**Вход в kinopub по коду (23.11).** «Профиль → Локальный движок → Источники →
kinopub»: под строкой источника — блок доступа. Если сессии нет: поле «Секрет
OAuth-клиента» (хранится открытым текстом рядом с остальными ключами, в
окружение движка попадает как `KINOPUB_CLIENT_SECRET` только при включённом
kinopub) и кнопка «Войти по коду». Кнопка живая, когда секрет **применён**
(движок получает его только вместе с запуском), движок готов и сам сказал
`kinopub.canLogin`. Нажатие открывает диалог: код крупно, «Открыть страницу»
(только https) и «Скопировать код» друг под другом, ниже «Жду подтверждения ·
код действует ещё N мин». Диалог спрашивает движок раз в 3 с, движок kino.pub —
не чаще разрешённого. После успеха движок перезапускается и kinopub поднимается
с сессией; «Выйти из kinopub» удаляет сессию и тоже перезапускает движок.

Что принципиально: секрет OAuth-клиента в приложение не вшит и не будет — у
kino.pub нет публичного клиента, секрет берётся из официального приложения, его
даёт человек; вход занимает отдельный слот устройства в аккаунте kino.pub (его
убирают на сайте в списке устройств); если kino.pub отзовёт сессию, вход надо
повторить. Файл сессии — `kinopub-session.json` в каталоге движка
(`KINOPUB_TOKEN_FILE`; настройки его не перекрывают), его читает и продлевает с
запасом `kpauth.Keeper`.

**Загрузки работают и в локальном режиме.** Утилита (`libkinopub.so`) получает
ссылку страницы тайтла `http://127.0.0.1:<порт>/#/title/<id>/s<N>e<M>` и сама
ходит к «платформе» — в движок: `/api/v1/titles/{id}` и
`/api/v1/episodes/{id}/manifest`, дальше сегменты идут через шлюз движка.
Утилита принимает `http://` и любой хост с портом, менять её не пришлось. Что
пришлось в приложении:
- **очередь по режимам.** Очередь, пауза, «качается сейчас» и «сдалась» лежат в
  файле настроек рядом с выбранной папкой (она общая), но у локального режима свои
  ключи (`queue_local`, …) и своя рабочая папка (`downloads-local`): id серий
  движка и сервера не совпадают, и задание одного режима, поднятое в другом,
  качало бы чужую серию. Опись скачанного — тоже своя (`files/local/library.json`);
- **адрес страницы — на актуальный порт** (`Downloader.rebase`): порт у движка
  новый на каждый запуск приложения, а задание могло пролежать в очереди с
  прошлого запуска и смотрело бы на мёртвый порт;
- перед запуском утилиты служба ждёт, пока движок будет готов; продление
  серверной сессии пропускается (у локального аккаунта токен не истекает);
- «готов» у движка теперь значит «площадки зарегистрированы»: `/api/v1/health`
  отвечает 503, пока они подключаются (но не дольше 6 с — площадка без сети не
  должна держать приложение). До этого холодный старт с отложенной загрузкой
  ронял первую попытку («provider не зарегистрирован»).
Скачивание — такая же нагрузка на источник, как просмотр, и это сказано в
отказе от ответственности.

**Настройки «серверной» части** (Профиль → Локальный движок): состояние и
«Перезапустить», источники (с ключами для тех, кому они нужны) и их статус
(«работает» / «подключается» / «отключён: причина»), прокси, подробный журнал,
кэш постеров, журнал движка, сброс данных. Изменения копятся в черновике и
вступают в силу кнопкой «Применить»: движок перезапускается и читает окружение
заново. Неверная настройка одной площадки (нет ключа, опечатка) отключает
только её и показывается в статусе, а не роняет движок
(`providers.BuildRegistryLenient`; сервер остаётся строгим).

**Бережность к чужим сервисам.** Тот же код, что у сервера, но другое
поведение по умолчанию — подчёркнуто скромное:
- в фоне ничего не ходит: нет обходов, нет опросов; площадки спрашиваются только
  когда человек ищет, открывает тайтл или смотрит;
- поиск **ступенями**: лучшая площадка первой, остальные — только если у неё
  нашлось мало (`ENGINE_SEARCH_MIN_HITS`, 3), и просим не больше
  `ENGINE_SEARCH_PER_SOURCE` (4) находок с площадки — у AnimeGo это прямая цена
  (карточка = страница, ~25 запросов за поиск из шести);
- **память запросов на диске** (`search_queries`): один и тот же запрос
  (нормализованный: регистр, дефисы, пробелы) на площадки не уходит
  `ENGINE_SEARCH_REPEAT_HOURS` (168 ч) — и после перезапуска. Запрос **без
  находок** помнится короче, 12 ч (`ENGINE_SEARCH_EMPTY_REPEAT_HOURS`): один
  случайный пустой ответ площадки (антибот, лимит) иначе закрыл бы запрос на неделю.
  Если сети не было или площадки ещё не зарегистрированы (спрашивать было некого),
  запрос не запоминается вовсе;
- всё найденное лежит в базе навсегда; поиск, у которого в каталоге уже есть
  тайтл с запросом в названии, площадок не трогает вовсе (найденная когда-то
  «Умпа-Лумпа» потом отдаётся из каталога);
- серии тайтла перечитываются при открытии не чаще `ENGINE_REFRESH_HOURS` (12 ч,
  в настройках 6 ч / 12 ч / 1 дн / 3 дн);
- кадры серий (по запросу на серию) выключены (`ENGINE_THUMBS`);
- кэш постеров 512 МБ по умолчанию: полученное не качается заново.
Счётчик исходящих запросов (`/engine/status`, виден в настройках) — на уровне
транспорта, а не соединений. Замер одного сценария («простой, поиск, повтор,
перезапуск, поиск без находок, открытие тайтла, кадры серий») на трёх
площадках: **69 запросов «как раньше» → 14 по умолчанию**; первый поиск 25 → 1,
повтор безрезультатного поиска после перезапуска 17 → 0, кадры 8 серий 4 → 0.
На телефоне те же 1 запрос на новый поиск и 0 на повторы, в том числе после
убитого и заново запущенного приложения.

**Отказ от ответственности** (`LocalModeNotice`): диалог перехода на этот режим
требует галочки «Я прочитал и понимаю», тот же текст всегда доступен в
настройках движка. Что в нём: сеть, VPN и нужные страны — на вас; это нагрузка
на чужие сервисы; историю никто не восстановит (хранится только на устройстве,
резервной копии нет); доступ могут закрыть в любой момент патчами против
сторонних клиентов; как есть.

**Сборка и проверка**
- `./web/apps/android/tools/build-bins.sh engine` → `libkinoengine.so` в
  `android/app/src/main/jniLibs/arm64-v8a` (cgo + NDK, `GOOS=android`, 16 КБ;
  16 МБ). `publish-apk.sh` теперь требует его в APK наравне с `libkinopub.so`.
- Копия рядом с настоящим приложением для проверки на телефоне:
  `./gradlew -PappIdSuffix=.check :app:assembleDebug` (пакет

## Свой сервер (2026-11-23)

Адрес сервера больше не зашит: вход → «Сервер · Сменить», профиль → «Сервер»,
на ТВ — строка в правом верхнем углу экрана входа и та же строка в профиле.
Решение и отвергнутое — [ADR-0016](adr/0016-own-server.md).

- `engine/ServerAddress.kt` — ввод → origin (без схемы — https; путь, запрос,
  фрагмент и порт по умолчанию отброшены; кириллица — punycode) и профиль данных
  `s_<12 hex sha-256>`; `KnownServers` — недавние, свежие первыми, до 8.
- `engine/ConnectionConfig.kt` — `serverUrl` (выбранный или вшитый),
  `needsServer` (сборка `-PkinoUrl=` без сервера → `ServerSetupScreen`),
  `profile`: `null` — вшитый сервер (прежние DataStore `kino`, filesDir,
  ключи очереди загрузок: обновление ничего не теряет), `local` — движок,
  `s_…` — выбранный. `setServer` = запись + перезапуск процесса (`AppRestart`).
- Раздельно по профилю: `TokenStore` (DataStore `kino_s_…`), `ModeContext`
  (`files/servers/s_…`: опись скачанного, StateStore, карточки),
  `Downloader.scoped`/`scopedDir` (ключи очереди `queue_s_…`, папка
  `downloads-s_…`). Вернувшись на прежний сервер, человек застаёт свой вход.
- `data/ServerProbe.kt` — визитка `/api/v1/server`, сервер старше визитки —
  по `/api/v1/health`; переадресация http→https запоминается; ошибки
  человеческими словами. Недавний сервер, не ответивший сейчас, можно выбрать
  «Всё равно подключиться» (откроется скачанное с него).
- Вход: режим регистрации из визитки (open — без кода, closed — без кнопки).
- Обновления — по-прежнему с вшитого сервера (ключ подписи сборки); перенос
  из старой оболочки и админка — только для вшитого/текущего сервера.
- http — только к серверу домашней сети (`ServerAddress.allowsCleartext`:
  частные IP, 100.64/10 Tailscale, имя без точки, .local/.lan/.home.arpa…),
  в интернет — только https; адрес без схемы для домашнего хоста откатывается
  с https на http. `network_security_config.xml` пускает http на уровне сети
  (диапазоны он не умеет), правило держит приложение. На http экран выбора
  предупреждает красным.

**Проверено (23.11):** все юнит-тесты приложения, 176 (новые: `ServerAddressTest`,
`ServerProbeTest`, ключи в `DownloaderTest`); на временном AVD (android-34,
arm64) против своего core (`REGISTRATION=open`, `SERVER_NAME`) — смена сервера
с перезапуском, регистрация без кода и вход, «Сервер» в профиле, уход на
боевой сервер (без визитки — опознан по health) и возврат на стенд без
повторного входа, раскладка `files/datastore/kino_s_….preferences_pb`,
«Всё равно подключиться» при погашенном стенде → офлайн, «Повторить» после
подъёма → главная; сборка `-PkinoUrl=` спрашивает адрес при первом запуске
(вставленная ссылка «адрес #/title/5» принимается); ТВ-экран входа при
960×540 dp — строка в углу, фокус пультом, окно выбора с клавиатурой.
**Не проверено:** настоящий Android TV и телефон пользователя, релизная сборка.
