# ADR-0005. Телеметрия: одна запись на просмотр; история просмотров приватна

**Статус:** принято · **Дата:** 2026-09-04

## Решение
Три слоя, не один:

1. **Операционные логи** — структурный JSON в stdout, ротация docker, 14 дней.
   Успешные запросы сегментов **не логируются**. В БД не кладутся никогда.
2. **`playback_sessions`** — одна строка на просмотр. Детали 90 дней, дальше
   схлопывание в суточные агрегаты.
3. **Суточные агрегаты** — килобайты, хранятся вечно.

## Обоснование объёма
HLS-сегмент 6 с; двухчасовой фильм ≈ 1200 сегментов видео + столько же аудио
= **~2400 запросов на просмотр**. Посессионная запись отвечает на те же
вопросы в 2400 раз дешевле.

Правило: **щедро к посессионным записям, скупо к пологовым логам.** Для
каждого поля назови вопрос, на который оно отвечает.

## Какие поля и почему
`player_impl` и `delivery_mode` — потому что полезная телеметрия совпадает
с ветвлениями архитектуры. У плеера два независимых движка (ADR-0002/0003);
без разбивки ребуферов по движку жалоба «на айфоне тормозит» неотлаживаема
в принципе. IP в `playback_sessions` не хранится.

## Приватность внутри семьи
**История просмотров — функциональные данные, не аналитика.** Живёт в
`watch_progress`, обслуживает «продолжить с места», не дублируется в
аналитический контур и **не имеет админского экрана**.

Причина не этическая, а целевая: платформа существует ровно потому, что общее
состояние в семейном аккаунте — плохо. Дашборд «что смотрел пользователь X»
воспроизвёл бы исходную проблему в худшей форме: раньше все видели общий
список, теперь один человек видит персональные списки всех.

Реализация — `internal/app/auth`: `Policy.CanReadProgress` отказывает даже
администратору без адресного `DiagnosticGrant` (временного, с причиной,
попадающего в журнал админских действий). Покрыто тестом.

Админка показывает операции и агрегаты: пользователь активен, последний вход,
ошибки, трафик. Популярность контента — счётчик на тайтл без `user_id`.
