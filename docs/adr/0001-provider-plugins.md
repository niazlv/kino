# ADR-0001. Провайдеры — плагины по gRPC-контракту, хостинг в двух режимах

**Статус:** принято · **Дата:** 2026-09-04

## Контекст
Площадок будет больше одной. Основной язык — Go, но гарантировать это на все
будущие провайдеры нельзя.

## Решение
Один контракт `api/proto/kino/provider/v1`, два режима хостинга из одной схемы:
in-process для Go, контейнер + gRPC для любого другого языка. Выбор режима —
строка в `CRAWLER_PROVIDERS`, не архитектурное решение.

Плагин **не имеет состояния и не знает инфраструктуру**: ни Postgres, ни Redis,
ни схемы БД. Всё, что ему нужно от платформы, приходит через обратный сервис
`PluginHost` (StateGet/Set, AcquireRateLimit, Log).

## Обоснование
- Код Go-провайдера одинаков в обоих режимах — за полиглотность не платим,
  пока она не нужна.
- Плагину на другом языке нужен ровно gRPC. Как только ему потребовался бы
  драйвер БД и знание схемы, «написать провайдер на Python» перестало бы быть
  дешёвым — а это и есть цель.
- `AcquireRateLimit` на хосте централизует вежливость: криво написанный плагин
  не задолбит площадку. При одном техническом аккаунте на семью это защита
  от бана, а не гигиена.

## Отвергнуто
- **hashicorp/go-plugin** — модель подпроцессов требует бинарник на ФС хоста,
  что конфликтует с контейнером-на-провайдера; своя супервизия вместо штатных
  рестартов docker; полиглот-история тоньше.
- **WASM** — работа кравлера это сетевой I/O, а исходящий HTTP из WASI
  болезненный. Инструмент не под задачу.
- **Self-registration с heartbeat** — лишняя машинерия при 2–5 провайдерах.

## Следствия
Контракт обязан быть **исполняемым**: `test/conformance` гоняет чёрный ящик
против любого провайдера, прохождение — условие приёма плагина. Документация
разъедется, тест — нет.
