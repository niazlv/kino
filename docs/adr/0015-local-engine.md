# ADR-0015. Локальный движок: один процесс на SQLite, без сервера

**Статус:** принято (проба) · **Дата:** 2026-11-23

## Контекст

Приложение бесполезно без личного сервера: core требует Postgres, Redis,
Docker и обходчика. Цель — режим, в котором платформа живёт целиком на
устройстве: «Подключение: сервер / это устройство». Первая проба — мак,
один процесс; упаковка под Android/iOS (gomobile) — следующий шаг после
удачной пробы.

Слои уже правильные (ADR-0006): `app/*` держит порты, `transport` не знает
про хранилища, `bootstrap` — единственное место встречи. `LazyCatalog`
(ADR-0008) уже умеет ленивый каталог: живой поиск по площадкам на запрос,
тайтл попадает в базу при открытии. Отсюда задача сжимается до: второй
адаптер хранения + второй композиционный корень.

## Решение

### Один процесс, два пространства в одном слушателе

`cmd/engine` собирает **и** пользовательское `/api/v1` (httpuser), **и**
медиашлюз (mediahttp) — как core и gateway вместе. Маршруты не пересекаются:
`/api/v1`, `/d/{token}`, `/s/{token}` — витрина; `/stream/*`, `/healthz` —
шлюз; `/internal/tickets/*` (grpcservice) — служебное. Служебное нужно
самому себе: `TicketRefresher` и доклад внешнего плеера — это HTTP-вызовы
на собственный адрес (`selfURL(Addr)`: порт из `ENGINE_ADDR`, хост — петля),
и mediahttp/grpcservice не меняются ни строчкой.

Конфликт с ADR-0002 (раздельный рестарт core и gateway) не возникает:
на устройстве оба «процесса» умирают вместе — разделять им нечего.

### SQLite вместо Postgres+Redis

`internal/adapter/sqlite` — второй адаптер под те же порты app-слоя.
Драйвер — **modernc.org/sqlite**: чистый Go, без cgo — только так сборка
двинется на телефон (gomobile) и iOS. Файл один (`ENGINE_DB`, по умолчанию
`./kino-engine.db`), режим WAL.

Схема — подмножество продовой, с теми же таблицами и колонками, что нужны
пользовательскому пути: `canonical_titles`, `canonical_episodes`,
`external_refs`, `episode_offers`, `title_names`, `users`, `sessions`,
`user_titles`, `watch_progress`, `search_history`, `share_links`.
Миграции — свой раннер на `PRAGMA user_version` и один встроенный SQL:
goose и 25 продовых миграций не нужны устройству, которое стартует с нуля.

`text[]` колонки (genres, countries) — JSON-текст: массивы читает код,
нечёткий поиск в SQL не нужен (ниже). `now()` в SQL не используется —
время ставит код (`kit.Clock`), как он и делает всюду остальное.

### Каталог ленивый, обхода нет

`LazyCatalog` переиспользуется как в core: живой поиск на запрос (offset 0),
`UpsertTitle` по каждому хиту, серии добываются при открытии тайтла,
досбор по номерам (IDLookup) при желании. Ничего из этого не требует
обходчика. НИКАКОГО `SyncService`/`Reconciler`/`Backfill` в движке нет.

Ленты — «только то, что получается без обхода»: «Продолжить», «Свежие
серии», «Я смотрю» считаются из прогресса и отметок (данные пользователя),
а разделы каталога (`browse`, жанры) показывают лишь тайтлы, уже попавшие
в базу — то есть открытые или найденные. Это осознанная бедность первой
страницы: каталог движка растёт от действий человека, а не от часов
обхода.

Поиск движка — `LIKE` по `title_names.name_key` и `title_norm` вместо
триграмм: каталог в базе исчисляется десятками, а не десятками тысяч, и
фаззи-степень не окупает pg_trgm. Три ступени поиска core (префикс →
внутри слова → похожесть) сжимаются до первых двух.

### Один пользователь и токен владельца

Движок обслуживает владельца устройства: на старте он заводит пользователя
(id=1) и сессию под **токен владельца**. Токен — единственный «пароль»:
его знают только владелец и приложение, запускающее движок. Откуда он:

1. `ENGINE_TOKEN` (≥ 32 знаков) — так задаёт приложение, запуская движок
   подпроцессом; в файл не пишется;
2. иначе файл `<ENGINE_DB>.token` (права 0600) рядом с базой — переживает
   перезапуск, поэтому сессия не плодится на каждый запуск, а cookie,
   выданная браузеру, не протухает;
3. иначе рождается новый случайный и пишется в тот же файл; тогда все
   прочие живые сессии гасятся (токены прежних запусков никому не нужны).

В базе, как у любой сессии, только хеш токена. Токен предъявляется обычной
cookie `kino_session` — вся аутентификация app-слоя остаётся как есть.
Первый раз браузер получает её по ключу: движок печатает в stderr (не в
структурный лог) ссылку `/engine/connect?key=…&next=<витрина>`; `next` — только
«свой» адрес.

**Почему не «сессия подставляется самим движком».** Первая версия пробы
подставляла cookie на каждый запрос — это снимало SameSite-защиту, на
которой в проде держится API: любая страница в браузере владельца могла
ударить в 127.0.0.1 (проверено: чужой Origin получал 204 на `logout`), а
dev-прокси на `0.0.0.0` раздавал сессию всей сети. Теперь:

- `loopbackGuard` пускает только свой Host (отсекает DNS-rebinding) и только
  свой Origin либо без Origin (так ходят приложение и `<video>`). Сверх
  петли — `ENGINE_ALLOWED_HOSTS` (например `10.0.2.2` для эмулятора);
- без токена — 401, как на сервере;
- служебный токен `/internal` — случайный на процесс (`SERVICE_TOKEN`
  можно задать явно для отладки).

**Выход, пароль, сессии.** `localModeGuard` отвечает 403 на logout, login,
register, смену пароля и удаление сессий: «Выйти» убивало единственную
сессию до перезапуска. `/me` отдаёт `"local": true` (в проде поля нет), и
витрина прячет подключение устройств, список входов, пароль и выход.
Инвайты, WebAuthn, TOTP, админка не монтируются вовсе: httpadmin не
собирается, `seedAdmin`/`resetTOTP` не существуют.

### Состояние ключуется на локальные ID, но внешние — рядом

Пользовательский стейт движка хранится на **локальных** канонических ID,
как в проде — так работают все сервисы без изменений. Рядом с `title_id`
лежит всё нужное для будущего слияния с сервером: `external_refs`
(provider_id, provider_ref, mal_id), `canonical_titles` (imdb_id, kp_id,
tmdb_id), эпизоды — сезон×серия и `episode_offers` с номерами площадок.
Канонические ID движка и сервера не совпадают и совпадать не обязаны:
синк строится на внешних ID и номерах, не на ID (синк — отдельная работа).

### Тикеты в памяти, телеметрия выключена

`TicketStore` — map с TTL: тикет короткоживущий, читает его тот же процесс
(Redis в проде нужен только потому, что core и gateway — разные процессы,
ADR-0002 оговаривает это как компромисс). Телеметрия сессий — no-op
`SessionSink`: `playback.Service` требует порт, но данных о сеансах на
устройстве не собираем (дух ADR-0005). Retention не нужен — ему нечего
убирать. `voicenames` — в памяти: обучение псевдонимам студий на одном
устройстве бессмысленно, разбор подписей работает и без таблицы.
segcache переиспользуется как есть (диск, по умолчанию выключен).

### Выключено и включено

Выключено: инвайты, WebAuthn, TOTP, админка, телеметрия, обходчик,
Reconciler, Shikimori-мост. AniSkip остаётся (он про просмотр, а не про
обход), share остаётся (ссылки без входа работают и локально).

Сеть: uTLS-отпечаток (`kit.LoadRoutes`, ADR-0003) остаётся — движок
выходит наружу теми же именованными маршрутами. Xray/VPN настраивается
маршрутом `EGRESS_ROUTES`/`KINOPUB_PROXY`, движок в это не вмешивается.

### Площадки для пробы

`PROVIDERS` по умолчанию — `anilibria,kinopub`: anilibria без всякой
авторизации (чистый JSON-API), kinopub — с токеном из окружения
(`KINOPUB_TOKEN`; опционально refresh через `KINOPUB_REFRESH_TOKEN` +
`KINOPUB_CLIENT_ID`/`SECRET`). Никакого обхода: только запросы по действию
человека.

### Вход в kinopub по коду (device flow)

Движок умеет получить свою сессию kino.pub сам: `POST /engine/kinopub/login`
берёт у kino.pub код, человек подтверждает его на странице kino.pub, движок
опрашивает не чаще, чем разрешил kino.pub (`slow_down` — реже), и пара токенов
пишется в файл `KINOPUB_TOKEN_FILE` — тот же, который читает `kpauth.Keeper` и
который сам продлевает пару с запасом. Дальше это обычный провайдер kinopub, ключ
руками не нужен. Ручки (`POST`/`GET`/`DELETE /engine/kinopub/login`) — только
владельцу; `/engine/status` отдаёт `kinopub: {session, canLogin}`.

Решения:

- **Секрет OAuth-клиента даёт человек.** У kino.pub нет публичного клиента для
  device flow: секрет берётся из официального приложения и в проект не вшит ни в
  каком виде (`KINOPUB_CLIENT_SECRET` из окружения; без него вход отвечает 409
  `no_secret` и ничего не отправляет наружу). `client_id` по умолчанию `android`.
- **Сессия своя и отдельная.** Вход занимает отдельный слот устройства в аккаунте
  kino.pub (убрать его можно на сайте в списке устройств), поэтому продлевать её
  безопасно — она ничья больше.
- **Бережно.** Опрос идёт по интервалу из ответа kino.pub, после пяти сбоев связи
  подряд вход прекращается, незавершённый вход просто истекает.
- Выход удаляет файл сессии (и `.lock`) — локально; слот на kino.pub человек
  убирает сам.

### Android: движок подпроцессом приложения

Бинарь `libkinoengine.so` лежит в APK рядом с `libkinopub.so` и запускается из
`nativeLibraryDir` — единственного места, откуда Android даёт исполнять файлы.
Сборка по рецепту утилиты: `GOOS=android` (у linux seccomp режет `faccessat2`),
**cgo + NDK** (имена резолвит система — частный DNS и VPN телефона, а не
публичные серверы напрямую, закрытые у части сетей), выравнивание 16 КБ.

Контракт приложения с движком: адрес — `127.0.0.1:<порт, выбранный приложением>`,
токен — `ENGINE_TOKEN` (приложение его и хранит), жизнь — на stdin
(`ENGINE_EXIT_ON_STDIN_EOF=1`: закрылся пайп — движок вышел). Приложение
надзирает процесс и перезапускает его на том же порту. Подробности и проверка
на телефоне — `docs/android-native.md`.

Данные режимов раздельны (id серий не совпадают), переключение — перезапуск
процесса приложения. Сервер-сессия при переключении сохраняется.

### Бережность к чужим сервисам

Движок работает с устройства человека и ходит на площадки его адресом, поэтому
по умолчанию он ведёт себя подчёркнуто скромно (подробности и замер — в
`docs/android-native.md`): в фоне не ходит; поиск ступенями (лучшая площадка
первой, остальные — если нашлось мало) с потолком находок на площадку; память
запросов на диске (`search_queries`) вместо десяти минут в оперативной памяти —
повтор не уходит на площадки неделю и после перезапуска (запрос без находок
помнится короче, 12 ч: случайный пустой ответ площадки не должен закрывать
запрос надолго), а запрос, на который никто не ответил (нет сети) или некого было
спросить (площадки ещё регистрируются), не запоминается;
найденное лежит навсегда; серии перечитываются при открытии не чаще заданного
срока; кадры серий выключены; исходящие запросы считаются на уровне транспорта
и видны в `/engine/status`. Всё это — настройки `LazyCatalog`
(`WithSearchMemory`, `WithEmptySearchRepeat`, `WithStaleAfter`) и композиционного
корня движка; сервер их не включает и живёт как прежде. «Готов» у движка значит
«площадки зарегистрированы»: пока они подключаются, `/api/v1/health` отвечает 503
(не дольше 6 с), и приложение держит запросы — иначе первый же запрос после
запуска (поиск, загрузка) попадал бы на пустой реестр.

Площадки на устройстве выбирает человек, поэтому сборка реестра мягкая
(`BuildRegistryLenient`): неверная настройка одной площадки отключает её и
попадает в `/engine/status` с причиной, а не роняет движок. Сервер остаётся
строгим.

### User-Agent: честный по умолчанию, настраиваемый человеком

Движок ходит на площадки с устройства человека, и представляться им он должен тем,
чем является, — приложением, а не чужим «Chrome на Маке», как это делает серверный
код (там подпись зашита в провайдерах: `embeds.UserAgent`, `anilibria`, картинки).
Подпись по умолчанию браузероподобная — части площадок и CDN без этого нечего
отвечать, — но кончается явной пометкой приложения и версии:

    Mozilla/5.0 (Linux; Android 10; K) AppleWebKit/537.36 (KHTML, like Gecko)
    Chrome/140.0.0.0 Mobile Safari/537.36 KinoPlatform-Android/0.2.14

Помет `KinoPlatform-Android/<версия>` приложение передаёт в `ENGINE_APP_UA`
(без него — `KinoPlatform-Engine`). Подписи провайдеров, которые сами представляются
браузером (`Mozilla/…`), заменяются; библиотечные, нужные площадке (`okhttp/…` у Filmix),
сохраняются и получают пометку в конце. TLS-отпечаток транспорта остаётся браузерным
(ADR-0003): CDN режут и по нему, и менять его ради «честности» значило бы сломать
воспроизведение, — это отдельный вопрос, и тут он не затронут.

Устроено в одном месте, провайдеры не меняются (`internal/bootstrap/engine/useragent.go`):

- общий слой транспорта маршрутов — для запросов, не привязанных к площадке (картинки,
  шлюз), и клиент каждой площадки поверх клиента её маршрута (`providers.Config.ClientWrap`);
- тикет: `Registry.WithUserAgent` кладёт в заголовки тикета ту же подпись, с которой шёл
  резолв, — шлюз предъявит её площадке (CDNVideoHub привязывает ссылку к подписи, и другая
  даёт 400). Подпись в тикете окончательна: общий слой транспорта её не переписывает.
  Сервер ни `ClientWrap`, ни `WithUserAgent` не включает и живёт как прежде.

**Подпись настраивает сам человек**, по каждой площадке отдельно: `ENGINE_UA_<ID>`
(`ENGINE_UA_ANILIBRIA`, `ENGINE_UA_ANIMEGO_ME`, …) и `ENGINE_USER_AGENT` — для всех
без своей; в приложении — «Локальный движок → Для опытных: User-Agent», без пересборки.
Мы не советуем её менять, но запрещать незачем — «положили ключ под коврик и
отвернулись»: заданное человеком уходит наружу как есть (площадка вправе отказать или
закрыть доступ — это на его совести, экран прямо так и говорит). Единственная проверка —
валидность заголовка: печатный ASCII, не длиннее 512; негодное отбрасывается с
предупреждением в журнал, подпись площадки сильнее общей. `/engine/status` отдаёт
`userAgent {default, custom}`: с чем движок ходит и где человек задал своё.

## Что не сделано

Сценарий «поиск → тайтл → тикет → просмотр → прогресс пережил перезапуск»
пройден руками на маке и на телефоне. Android-упаковка и экран «Подключение»
сделаны (см. выше). Не сделано:

- iOS: движок там возможен только внутри процесса (gomobile/c-archive, нужен
  cgo), фон замораживает localhost-сервер;
- вход из самого приложения для Filmix и Alloha: ключ у них вводится вручную
  (у kinopub вход по коду есть — см. выше; на настоящем kino.pub он не
  проверен: нужен секрет клиента и аккаунт человека);
- синк локального состояния с сервером (по внешним ID);
- телевизор;
- Windows-сборка движка: мешает `syscall.Flock` в `kpauth` (код сервера).

## Следствия

- Витрина и нативные клиенты работают без изменений: ответы — те же
  структуры, тикет — тот же.
- Первый поиск медленный (живые площадки, ~10 с), повторный — из базы.
- Не упало в базу — не существует: без сети движок умеет только то,
  что уже открывали.
- Боевой сервер и docker-compose не затрагиваются: всё новое живёт в
  `internal/adapter/sqlite`, `internal/bootstrap/engine`, `cmd/engine`.
