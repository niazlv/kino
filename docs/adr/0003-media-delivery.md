# ADR-0003. Доставка медиа: проксирование по умолчанию

**Статус:** принято, подтверждено измерением · **Дата:** 2026-09-04

## Решение
**Полное проксирование** (`DELIVERY_MODE_PROXY`) — рабочий режим. Redirect
оставлен за флагом конфига, но по умолчанию выключен: доступность CDN
у клиента непредсказуема, а API площадки блокируется, из-за чего резолв
в любом случае идёт через VPN на сервере.

Байты тянет **сам gateway** браузерным транспортом с подделанным TLS-отпечатком
(`pkg/browserhttp`), а не nginx. Первоначально здесь было решение отдавать
выкачку nginx через `X-Accel-Redirect`; оно отменено — nginx работает поверх
OpenSSL и предъявит CDN тот отпечаток, который душат. Подробности ниже.

## Обоснование
Масштаб делает трафик нерелевантным: 4 потока 1080p ≈ 40 Мбит/с. За это
снимается целый класс проблем — CORS, IP-привязка, протухание, утечка ссылок,
расхождение поведения iOS и Chrome. Для инфраструктуры на одного разработчика
сложность дороже байтов.

Довод «Go не должен держать соединения» здесь не работает: держать их
приходится, потому что только его транспорт проходит фильтрацию по отпечатку.
На четырёх одновременных потоках это четыре `io.Copy` — цена, которой можно
пренебречь, в отличие от заблокированной выкачки.

## Результаты фазы 0 (измерено на живом kinopub)

| Пункт | Результат | Следствие |
|---|---|---|
| (г) заголовки | **не нужны**, голый GET отдаёт 200 | `upstream.headers` пуст; оговорка ADR-0004 закрыта — gateway не касается секретов. **Но см. раздел про TLS-отпечаток: пробник ходил обычным Go-клиентом, и для длительной выкачки этот результат не показателен** |
| (б) CORS | `Access-Control-Allow-Origin: *` | технически прямая отдача возможна, но см. раздел про блокировку |
| (в) TTL | **24 часа**, полем `files[].expires_at` в ответе API | двухчасовой фильм укладывается в один тикет с запасом |
| (а) привязка к IP | **не проверялась и не требуется** | вопрос снят сетевой доступностью, см. ниже |

Дополнительно измерено и учтено в коде:

- **Мастер-плейлист на `api.service-kp.com`, сегменты на
  `<uuid>.ams-static-NN.cdntogo.net`** — хост меняется и по номеру сервера,
  и по uuid контента. Точное сравнение в `allowed_origins` давало бы битый
  плеер при внешне живом тикете, поэтому сравнение суффиксное, с обязательной
  границей метки (`cdntogo.net` не пропускает `evil-cdntogo.net`).
- **8 файлов на видео: 4 качества × два кодека, h265 И h264.** Проблема HEVC
  решается выбором рендишена через `ClientProfile`.
- **12 аудиодорожек и 10 субтитров** на популярный фильм. Переключение
  озвучек — обязательное требование, не опция.

## Решающий фактор: площадка заблокирована в РФ

Доступ к kinopub и его CDN из России возможен только через VPN. Отсюда
следствие сильнее всех измерений выше:

Блокируется в первую очередь **сайт и API** (`api.service-kp.com`); про CDN
такого утверждать нельзя — замер с этой машины показал открытый TCP:443
и к API, и к `cdntogo.net`. Ранее здесь стояло «браузеры не дотянутся до CDN
вообще»: это было обобщение, а не измерение, и оно снято.

Что отсюда следует надёжно:

- **Резолв обязан ходить через VPN-выход.** Кравлер и выпуск тикета
  упираются в заблокированный API, и это не зависит от доступности CDN.
- **Доступность CDN у клиента непредсказуема** и меняется от провайдера
  к провайдеру и со временем. Строить доставку на допущении, что у каждого
  домашнего CDN открыт, значит получать «у меня не грузится» без диагностики.

Проксирование остаётся правильным выбором, но по совокупности причин —
контроль авторизации, протухание, утечка ссылок, TLS-отпечаток (ниже) и
непредсказуемая доступность CDN у клиента, — а не потому, что CDN заведомо
недостижим. Побочно снят открытый пункт (а): резолв и отдача идут через один
egress, так что привязка к IP, если она есть, выполняется сама собой.

Следствия для эксплуатации:

- **VPN нужен серверу, а не клиентам.** Домашние ходят на твой сервер по
  обычному интернету. Это и есть главная выгода схемы для семьи: настраивать
  VPN на каждом телевизоре и телефоне не придётся.
- **Пропускная способность туннеля — узкое место.** Четыре одновременных
  потока 1080p это около 40 Мбит/с через VPN. Требование к каналу, не к серверу.
- **HTTP-клиент провайдера обязан приходить снаружи**, чтобы через него можно
  было задать прокси. Адаптер не создаёт свой клиент.

## TLS-отпечаток: nginx для выкачки с CDN не годится

CDN и Cloudflare режут скорость и блокируют по JA3/JA4-отпечатку, а
стандартный `crypto/tls` в Go даёт отпечаток, который под это попадает.
Утилита-загрузчик тянет сегменты только клиентом с подделанным отпечатком
Chrome (`pkg/browserhttp`, uTLS) — это её опыт, оплаченный столкновением
с проблемой, а не предосторожность.

**Пробник фазы 0 ходил обычным `net/http`.** Один запрос прошёл, но
расхождение проявляется на длительной выкачке, поэтому пункт (г) следует
читать как «заголовки не требуются», а не как «транспорт подходит».

Отсюда правка, отменяющая раннее решение этого ADR:

> Схема «Go принимает решение по тикету, а байты гонит nginx через
> `X-Accel-Redirect`» **неприменима к выкачке с CDN**: nginx работает поверх
> OpenSSL и предъявит ровно тот отпечаток, который душат. Апстрим-запросы
> обязан выполнять сам gateway браузерным транспортом.

Что это меняет и чего не меняет:

- **Проксирование делает Go.** На семейном масштабе это не проблема:
  четыре одновременных потока — четыре `io.Copy`, а не нагрузка, ради
  которой затевался вынос в nginx.
- **Дисковый кеш nginx для апстрима теряется.** Кешировать придётся самим
  либо не кешировать вовсе: при суточном TTL ссылки и повторных просмотрах
  в пределах семьи выигрыш кеша скромный.
- **Для `DELIVERY_MODE_LOCAL` nginx остаётся уместен**: там отдаётся файл
  с локального диска, никакого CDN и никакого отпечатка.
- **Параллельность сегментов ограничена.** Загрузчик держит 4 — это
  разумный дефолт и для gateway, и заодно вежливость к площадке.

## Пересмотр допущения

Исходно ADR исходил из «ссылка живёт 30 минут, фильм 2.5 часа», откуда следовала
необходимость проактивного обновления на горячем пути. При суточном TTL это
допущение неверно: обновление остаётся **страховкой**, а не механизмом,
и приоритет у него ниже.

## Зафиксированные ограничения
- **Нативный HLS на iOS не подставляет заголовки** → авторизация медиа только
  в подписанном URL или same-origin cookie, никогда в `Authorization`.
- **`ip_bound`** → резолв и отдача обязаны идти с одного egress IP.
- **Переписывание m3u8** должно покрывать все теги с URI, включая
  `EXT-X-MEDIA` (пропуск = «видео есть, звука нет»), `EXT-X-KEY`, `EXT-X-MAP`.
- **`allowed_origins`** — защита от SSRF: тикет приказывает нашему серверу
  сходить по URL, редиректы за пределы списка отвергаются.

## Транскодинг
Не делаем на лету. Нужен **ремукс** (`ffmpeg -c copy`). Точечный транскод под
HEVC, который планировался как единственный законный случай, **не требуется**:
площадка отдаёт h264-рендишен для каждого качества. Достаточно выбора через
`ClientProfile`.
