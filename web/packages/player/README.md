# @kino/player

Ядро видеоплеера. **Отделяемый пакет**: ничего не знает о платформе — ни об
API, ни об авторизации, ни о тикетах, ни о модели прогресса.

## Что делает отделяемость настоящей, а не декларируемой

1. **Никаких зависимостей `@kino/*`.** Проверяется в CI
   (`scripts/check-boundaries.sh`). Пакет публикуется в npm как есть.
2. **Плеер не ходит в сеть за состоянием.** Он не знает эндпоинтов. Прогресс
   уезжает через инжектируемый `ProgressSink`, а не через встроенный `fetch`.
3. **Вход — `PlayerSource`**, обычный объект: URL, дорожки, стартовая позиция.
   Откуда он взялся (тикет, статический файл, локальный ремукс) — не его дело.
4. **Свой демо-стенд без бэкенда**: `pnpm demo` играет произвольный m3u8.
   Это не витрина, а рабочий инструмент — плеер разрабатывается и чинится
   без поднятия всей платформы. И это же ежедневная проверка, что связи
   с приложением не завелись.
5. **Ядро на ванильном TS**, React — тонкая обвязка в `./react`. Плеер не
   приварен к фреймворку и переживает смену UI.

## Ключевая внутренняя граница: Engine

`hls.js` не работает в Safari на iPhone — там играет только нативный HLS.
Это не деталь реализации, а два независимых кодовых пути, поэтому они разведены
интерфейсом `PlaybackEngine`, а не `if` внутри плеера:

    PlaybackEngine
      ├── HlsJsEngine   — MSE: десктоп, Android
      └── NativeEngine  — <video src="...m3u8">: iOS Safari

Каждый движок сам сообщает `impl`, и это же значение уезжает в телеметрию
(`playback_sessions.player_impl`). Без разбивки метрик по движку жалоба
«на айфоне тормозит» неотлаживаема: не отличить проблему сети от бага
в одной из двух реализаций.

Из-за нативного пути авторизация медиа не может жить в HTTP-заголовке —
нативный плеер их не подставляет. Только подписанный URL или same-origin
cookie. Это ограничение зафиксировано в ADR-0003.
